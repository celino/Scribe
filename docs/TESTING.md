# Testing Scribe

Every feature in the README has an ID (`F01`...`F17`) in [`tests/FEATURES.md`](../tests/FEATURES.md), the layer that proves
it, and the test that does. `tools/validate.py` fails the build when the README, the matrix and the tests drift apart.

You can go as far as you like. Each level needs more than the one before.

| Level | What runs | Needs | Where |
|---|---|---|---|
| 1 | Unit tests of the ledger core and the decision rules, the Python tool tests, the matrix check | `dotnet` SDK 8, Python 3 | any machine, GitHub Actions |
| 2 | Compile the plugin | the same, plus a KSP 1.12.5 you own (the build references its assemblies) | your machine |
| 3 | Scripted rounds in a running game, with PASS/FAIL assertions | KSP 1.12.5, a display, Docker or `dotnet` | your machine |

KSP and Unity cannot be redistributed, so this repository carries no game files, no game DLLs and no Docker image with
Unity. What it carries is the recipe.

## Level 1: no game needed

```sh
python3 tools/validate.py                                  # README, matrix, tests, language
python3 -I -m unittest discover -s tests -p 'test_*.py'    # remove-from-save.py (F15)
dotnet test tests/Scribe.Tests/Scribe.Tests.csproj -warnaserror \
  --settings tests/coverlet.runsettings
```

The unit tests are named by feature (`F03_...`), so a failure says which promise broke. The core (`Source/Core`) is plain
C# with no KSP types; the module only adapts KSP events and `ConfigNode` to it.

## Level 3: rounds in a real game

Each round starts the game, loads a small synthetic save, lets a test-only add-on drive the game, and prints lines like
`ASSERT F07 PASS first change after the quickload is exactly -300`. `tests/ingame/check_round.py` turns the log into an
exit status. It also fails on a missing assertion, a driver that never finished, an assembly that failed to load, or an
exception that names Scribe.

| Round | Proves | Scenario |
|---|---|---|
| `tx` | F01: eight known transactions, right delta and balance | minimal |
| `revert` | F07: a quickload takes the ledger back with the save | minimal |
| `flight` | F08, F10: launch, destruction, recovery, kerbal death, contract | minimal |
| `dock` | F09: two real vessels coupled, no false `destroyed` entry | minimal |
| `bench` | F13, F03: cost per event, the 5,000-entry cap | minimal |
| `menu` | F12: the module adds itself to a save that never had it | minimal |
| `noscribe` | F14: the game loads without the mod and the ledger stays in the save | minimal |
| `kct` | F11: technology and facility through Kerbal Construction Time | kct |

### 1. A throw-away install

```sh
tools/ksp-dev-create.sh --ksp "<your KSP 1.12.5 dir>" --dest ~/ksp-scribe-test --scenario minimal
```

It checks the game build (`03190`), hard-links the game files (about 3 MB extra on disk; `--copy` for another
filesystem), keeps only Squad, SquadExpansion and the scenario's mods in `GameData` (installed with CKAN at the versions
pinned in `tests/ingame/scenarios.json`), copies the synthetic save and installs the plugin. Your own install and saves
are never touched. To undo: delete the folder.

The synthetic save (`tests/ingame/save`, 64 KB) is generated by `tests/ingame/make-save.py` from nothing: a new Normal
career with 100,000 funds, 50 reputation, 100 science, the four default kerbals, one stock probe. No personal data.

### 2. One round

```sh
DISPLAY=:0 tools/run-ingame.sh --install ~/ksp-scribe-test --round flight
```

The runner builds the driver (with `dotnet`, or with the Docker image if there is no `dotnet`), puts it in `GameData`,
starts the game, waits for the driver's `done`, stops the game, restores the save, removes the driver and prints
`RESULT PASS` or `RESULT FAIL`. Output (log, saved files, result) goes to `ksp-test/<round>/`.

### 3. Everything

```sh
DISPLAY=:0 tools/run-ingame-all.sh --ksp "<your KSP dir>"
```

It creates one install per scenario, runs every round of the scenario and prints one line per round. A full pass takes
about 20 minutes.

### Display and rendering

The game needs a display. A real one (your desktop, a GPU) is the supported setup: the whole suite runs in about 20
minutes and each round in under two. A virtual display with software OpenGL (Xvfb and Mesa, the image in
`tests/ingame/docker`) also works for the simplest rounds, but scene loads stall for many minutes and sometimes forever, so
it is not reliable for the rest. The runner retries a stalled attempt from a fresh save (`ATTEMPTS`, default 3) and kills
a silent one after `IDLE_S` seconds (default 300). Build the image with
`docker build -t scribe-ksp-test tests/ingame/docker` if you want to try it; it contains no game files.

### Notes for people who write rounds

- **Add a feature, add an ID.** A new row in `tests/FEATURES.md`, a README phrase, an `Assert("Fnn", ...)` in the driver or a
  unit test with the same prefix. `validate.py` checks all three.
- **Seeded scenarios.** The driver loads the save its own way, which skips some scenario nodes that the normal "Resume
  game" path would create. The runner seeds the nodes the round does not test (Scribe, and Kerbal Construction Time for
  `kct`). `menu` leaves the Scribe node out on purpose; it proves the module adds itself, not a click through the menu.
- **Vessels are Unity objects.** After a merge the old vessel compares equal to `null`. Keep a plain `bool` if you need
  to remember that it existed.
- **Unit tests cannot catch loading problems.** A first version of the core was `netstandard2.0` only and passed every
  unit test, but KSP could not load it (there is no `netstandard.dll` in the game). Only a round in the game caught it.
  The core is built for `net48` (shipped) and `netstandard2.0` (tests).
- **No Kerbal Construction Time reference.** Scribe finds it by name at run time. Only the `kct` driver references it.
